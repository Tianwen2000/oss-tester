# OSS 使用统计、资源包与支付测试计划

## 1. 测试目标与边界

- 目标：验证 OSS 使用统计、资源包抵扣、资源包状态和支付金额链路的正确性、幂等性与可追溯性。
- 范围：使用统计、资源包管理、报价/订单/支付/账本/资源包开通联动。
- 边界：不把统计页面当作实时计费账单；统计延迟或展示精度差异先按 `WARN` 处理。
- 安全：专用测试账号、专用 Bucket、隔离测试前缀；禁止直接在生产环境批量购买或制造大额流量。

## 2. 测试准备

- 在控制台创建专用测试 Bucket、测试账号和最小权限身份。
- 准备小规格、低金额资源包；购买前设置预算上限、审批人和告警。
- 记录测试前基线：桶数、对象数、存储容量、读请求、写请求、公网下行、CDN 回源流量。
- 记录资源包订单号、计费项、规格、地域、剩余量、生效时间和到期时间。
- 所有测试对象使用唯一前缀：`metering-test/<run-id>/`。
- 明确统计时间口径、时区、计量周期和平台延迟；截图中的统计提示说明数据可能不是实时值。

## 3. 使用统计

### 3.1 统计指标

- 存储桶数量、对象总数、存储容量。
- 公网下行流量、CDN 回源流量。
- 读请求数、写请求数，以及失败请求/重试请求是否计入的口径。
- 本月、近 7 日、近 30 日和自定义日期范围。

### 3.2 确定性负载

单独执行固定次数的计量脚本，避免复用完整回归测试的重试、分页和自动清理请求：

- 上传 20 个不同 Key，覆盖写 5 个 Key，删除 2 个 Key。
- 上传总计 60 MiB 的确定性内容，完整下载 1 MiB 对象 20 次，再 Range 下载 2 MiB。
- 固定执行 100 次 Head、30 次 Get、20 次 List、50 次 Put、10 次 Copy、10 次 Delete。
- 创建 Multipart，上传 3 个分片后暂停；分别观察未完成分片是否计入临时存储和请求。
- 如验证 CDN 回源，制造约定次数的 MISS，并结合 CDN/源站日志核对回源流量。

### 3.3 统计断言

- 对象数、容量、流量和请求数的增量与理论负载一致，允许平台公开的采样误差和延迟。
- 覆盖写不增加对象数，但会增加写请求和可能的存储计量。
- 删除后对象数和容量最终回落；版本控制桶要分别核对版本和删除标记。
- 多桶测试时只计入当前账号和选定范围，不得串入其他租户或业务桶。
- 日期筛选、图表单位、Tooltip、图例开关、刷新和分页显示正确。
- 每隔 15～30 分钟观察，最长覆盖一个完整统计周期；记录首次出现值和最终稳定值。

## 4. 资源包管理

### 4.1 列表和状态

- 核对资源包名称、订单号、地域、来源、计费项、规格、用量、生效时间和到期时间。
- 验证“有效/无效”页签：未生效、使用中、已耗尽、已过期、退款或取消状态分类正确。
- 验证筛选、排序、分页和总数；生效时间、到期时间排序不能错乱。
- 东京等测试 Bucket 必须命中资源包适用地域；地域不匹配时不得错误抵扣。

### 4.2 抵扣和生命周期

- 存储容量增长后，存储容量包用量按产品规则增加。
- 公网下载后流量包扣减；CDN 回源是否抵扣以产品计费规则和账单为准。
- 固定批次读写请求后，读写请求包次数按规则扣减。
- 多个同类资源包并存时，验证先到期优先或平台声明的使用顺序。
- 首个资源包耗尽后自动切换下一个；到期后停止抵扣，不产生负余额。
- 购买前已产生的用量不能被新资源包追溯抵扣，除非产品明确声明支持。

## 5. 支付金额与订单（P0）

### 5.1 金额模型

- 后端使用整数最小货币单位计算，例如 `$4.50 = 450 cents`，禁止浮点金额。
- 以截图场景为例：原价 `$8.00`、优惠 `$3.50`、应付 `$4.50 USD`，必须满足 `8.00 - 3.50 = 4.50`。
- 商品页、报价、确认页、订单、支付请求、支付流水、账户账本和资源包开通记录必须金额、币种一致。
- 生产环境禁止把前端展示价格作为扣款依据；应付金额必须由服务端重新计算并绑定订单。

### 5.2 必测场景

- 前端篡改价格为 `$0.01`：服务端拒绝或忽略篡改值。
- 重复点击购买、重复提交订单、重复支付回调：只生成一个有效资源包，只扣一次款。
- 支付超时或页面断网：不得引导用户盲目重新支付，应查询原订单最终状态。
- 余额不足、支付失败、取消订单：不扣款、不生成有效资源包，状态清晰。
- 支付成功但开通失败：必须补偿、退款或进入人工处理队列，不能出现“已扣款但无资源包”。
- 开通成功但扣款失败：资源包不得进入可用状态。
- 优惠过期或价格变化：下单时重新报价并要求确认，不能静默换价。
- 地域、规格、容量、有效期和计费项必须与下单内容一致。

### 5.3 金额对账

至少完成三方对账：

1. 服务端订单/报价：原价、优惠、税费、应付、币种。
2. 支付渠道流水：支付金额、币种、支付状态、网关流水号。
3. 账户账本和资源包：余额变更、资源包实例、开通状态和抵扣范围。

任何一分钱差异、重复扣款、币种变化、订单与资源包不一致，都直接判 `FAIL/P0`，不能降级为 `WARN`。

## 6. 执行计划

1. **基线阶段**：记录控制台、账本和资源包原始状态，确认预算与审批。
2. **负载阶段**：执行固定对象、流量和请求负载；保留客户端成功数和时间戳。
3. **观察阶段**：每 15～30 分钟记录统计页面、资源包用量和服务端计量数据。
4. **支付沙箱阶段**：使用最小金额或测试支付完成报价、订单、回调、开通和退款/取消链路。
5. **稳定阶段**：跨至少一个计量周期核对最终值、资源包抵扣和到期/耗尽切换。
6. **清理阶段**：仅删除 `metering-test/<run-id>/`，确认容量和对象数回落，不删除桶或其他对象。

## 7. 证据与判定

- 证据：控制台截图、统计接口响应、理论负载清单、订单号、支付流水号、账本流水、资源包实例 ID、回调日志和时间线。
- `PASS`：理论值、平台值和账务值一致，或符合已确认的延迟/精度规则。
- `FAIL`：金额差异、重复扣款、资源包错开通、数据串租户、统计核心值错误或状态不一致。
- `WARN`：统计延迟、展示精度、厂商未公开计量口径等非财务核心问题。
- `SKIP`：沙箱未提供某支付方式、地域或资源包类型不适用。

## 8. 发布门禁

- 金额链路、幂等、回调重放、失败补偿和三方对账全部通过，才允许进入发布评审。
- 任何 P0 金额问题立即停止真实购买和批量回归，冻结相关功能并轮换测试凭证。
- 真实生产小额购买必须单独审批、设置预算上限，并由人工确认后执行；自动化只做只读核对和沙箱验证。
